# OpenDiag: project conventions

- **Spec:** the master development prompt + the owner's confirmed architecture decisions (Windows and Android first-class; separate diagnostics and configuration; compatibility database from Phase 1; Phase 1 criteria in `docs/backlog.md`). Record notable choices in `docs/decisions.md`.
- **Honesty rules:** never fabricate ECU definitions, parameters, specs, test results or compatibility. Statuses: Implemented and tested / Implemented but not hardware-verified / Partially implemented / Simulated only / Planned / Unsupported. Only real-hardware evidence (per OS) moves a function to "tested" (`docs/compatibility.md`, `crates/opendiag-engine/src/catalog.rs`).
- **Safety:** every non-read request goes through `opendiag-safety` (`may_send` + `Authorization`); J1939 requests only via `may_request_pgn` (read-only list). Never add a path around it; level 4 is never implemented. Clearing codes: `crates/opendiag-engine/src/clear.rs`.
- **Owner** is not a professional developer and uses Windows: explain in plain language, give explicit steps, and at the end of a milestone say how to run it and what to test by hand.
- **Layout:** Rust crates in `crates/` (core, isotp, obd, safety, driver (the `Driver` trait), elm327, kline (raw K-line + experimental Honda), j1939 (J1939 parsing/decoding, read only), transport, sim, knowledge, definitions (incl. the connector catalog, generated by `scripts/gen_connectors.py`), store, engine, api, cli); UI in `apps/ui` (React + TS, every text via `t()`); Tauri shell in `apps/desktop/src-tauri` (Android project in `gen/android`); Android USB/Bluetooth bridge in `plugins/tauri-plugin-opendiag-transport`.
- **UI ↔ engine:** JSON commands (`Cmd` in `crates/opendiag-api/src/lib.rs`) mirrored by `apps/ui/src/types.ts`. Tauri IPC in the app; `opendiag serve` (127.0.0.1:7878) in a browser.
- **Commands:** `cargo test`; `pnpm --filter @opendiag/ui typecheck|test|build`; `pnpm tauri dev|build`; `pnpm tauri android build --apk`.
- **Privacy:** local only, VIN masked in exports and hidden in logs by default; nothing uploads automatically. Internet access only from the app shell: the optional update check (`apps/desktop/src-tauri/src/update.rs`) and opt-in result sharing (`community.rs`; data built by `crates/opendiag-engine/src/share.rs`, received by `services/feedback`, a Cloudflare Worker + D1). Shares never contain the full VIN or free text; simulator results are never shared; community data is at most `community_reported`.
- **Changelog:** every user-visible change adds a line under `## Unreleased` in `CHANGELOG.md` (Added / Changed / Fixed / Removed, plain language) in the same commit. The release workflow turns that section into the release notes (the app's "What's new") and renames it to the build (`scripts/changelog.py`).
- **Suggestions:** the app's Suggest a feature page posts to `services/feedback` `/v1/suggestions`, which opens a GitHub issue (labels `feature request`/`bug` + `from app`) with the Worker secret `GITHUB_TOKEN`.
- **Data:** knowledge and definitions are JSON with sources; validated by tests (`cargo test -p opendiag-knowledge`, `opendiag validate-definition`).
- **Never trust the order of a list from an outside service** (GitHub releases, RSS feeds, ERP/API lists, file listings): when code needs the "newest", "latest" or "first", sort by the date or version field itself, and give it a test with the list in a shuffled order. Lesson from OpenDiag 2026-10-21: GitHub listed test-build-10 after test-build-5, the update check took the first entry and offered no update (see OpenDiag `docs/decisions.md`).
